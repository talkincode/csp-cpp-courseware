# 键盘可达与焦点可见手工端到端验收（全部 40 课）

这份清单管的是「整节课不用鼠标也能走完，而且始终看得见焦点在哪」。它和
[`flow-manual-checklist.md`](./flow-manual-checklist.md) 不互相替代——那边验「路走得通不通」（进度、跳步、小测、
存不存本地），这边验「键盘用户走同一条路会不会撞墙」：焦点会不会突然消失、按钮只靠鼠标才点得动、
弹层关掉后焦点飘到文档开头、提交之后键盘够不到复习入口。

这是零基础学习者的真实处境：很多孩子第一次用电脑就是在笔记本上只用键盘练习，鼠标摸不到的时候
课件必须照样能用。`AGENTS.md` 里「维持键盘可达、清晰焦点态」是硬要求，这份清单就是那条要求的现场做法。

## 前置条件

在仓库根目录运行 `bun run dev`，从 <http://localhost:4173/> 进入任意一课。**全程不碰鼠标**，只用
`Tab` / `Shift+Tab` / `Enter` / `Space` / 方向键 / `Esc`。需要从头开始时按 `F5` 刷新，或清掉该课的本地存储键
`csp-cpp-sN-NN-progress-v1`。

## 每课固定复验的 8 项

前四项是「焦点看得见、顺序讲道理」，后四项是「每个控件都能用键盘真的操作」：

1. 按 `Tab` 从页面开头走到结尾再绕回开头，每一个停靠点都能看出焦点在哪（有可见焦点环，不是 `outline: none`）。
2. 没有用正数 `tabindex` 把元素从自然 `Tab` 顺序里拽出来打乱顺序。
3. 没有把原生控件（`button`、`input`、`a`）用 `tabindex="-1"` 排除出 `Tab` 顺序。
4. 没有「看着能点、键盘够不到」的元素（例如只能用鼠标点的 `div` 当按钮）。
5. 音效开关：`Space` 能切换开与关，`aria-pressed` 与屏幕上的文案同步变化。
6. 词条：`Enter` 打开词条面板，`Esc` 关闭，并且关掉之后焦点回到刚才那个词条（不是飞回文档开头）。
7. 步进门闩：`Tab` 够得到，但 `Enter` 与 `Space` 都推不动进度，面板照旧藏着，状态区域说明为什么。
8. 步进轨道上每一步都在 `Tab` 顺序里，包括还锁着的那几步（学习者能先用键盘发现它们）。

## 键盘深路径每课固定复验的 4 项

结构检查只证明「每个零件都没坏」，深路径证明「只用键盘真的能通一节课」。默认对 S1-02（第一阶段
微编程）与 S3-01（第三阶段）各走一遍：

1. 只用键盘走到微练习空位、逐字符敲进去、按检查，进度真的往前走了（不是只把字敲进草稿）。
2. 每题都按 `Space` 作答，答完焦点仍留在同一题组里（没有掉回文档开头，不用重新找回题目）。
3. 没答完时提交按钮是原生 `disabled`（键盘够不到，不是能按但没反应）；答满后键盘提交能拿到得分与逐题解析，
   并且焦点交给结果区（`#quizResult`），读屏会直接念到得分。
4. 提交后不能重复提交，且「换一套题」仍然够得到——复习出口没被键盘堵死。

## 自动化复验记录

```bash
CSP_E2E_KEYBOARD_LESSONS=s3-01 bun tests/e2e/keyboard-cdp.ts    # 结构检查只跑 S3-01，深路径自动收窄成 S3-01，共 12 项检查
CSP_E2E_KEYBOARD_DEEP=s1-05 bun tests/e2e/keyboard-cdp.ts       # 结构检查仍跑全部 40 课，深路径只留 S1-05，共 324 项检查
```

深路径只会跑「结构检查也覆盖到」的课，所以指着别的课不会多跑一节；`CSP_E2E_KEYBOARD_DEEP` 留空会退回默认的
S1-02 与 S3-01 两课，脚本没有「只跑结构检查」这一档。全量复验一次跑完全部 40 课：

```bash
bun run e2e:keyboard        # 40 课各 8 项结构检查 + 两课各 4 项深路径检查 = 328 项检查
```

## 这一轮修掉的两个焦点丢失点

写这份清单的起因是「键盘可达」此前**一条断言都没有**。脚本第一次跑就量出两个真实缺陷，都在全部
40 课里存在（由同一份样板生成）：

- **作答后焦点掉回文档开头。** 小测的 `renderQuiz()` 每答一题就用 `quizForm.innerHTML = ...` 重画题面，
  被按下的那个单选项随之被销毁，浏览器只能把焦点退回文档主体。修法：重画之后按 `name` + `value`
  找回刚答的那一项，用 `focus({ preventScroll: true })` 把焦点交还回去（`focusQuizAnswer`）。
- **提交后焦点掉回文档开头。** 提交成功那条路会把提交按钮设成 `disabled`，浏览器对 `disabled` 的元素
  会主动移走焦点，于是正当得分与逐题解析出现、学习者最需要读它的时候，焦点反而回到了页面顶部，
  键盘用户要再按十几次 `Tab` 才能摸回来。修法：给结果区 `#quizResult` 加 `tabindex="-1"`（可聚焦、
  不进自然 `Tab` 顺序），提交成功与「题库不可用」两个分支结束后都把焦点交给它（`focusQuizResult`），
  `aria-live` 状态区同步念出结果。

这两个缺陷都由 `tests/keyboard-access-contract.test.ts` 在 `bun test` 里上锁：它按 `courseData` 逐课扫页面，
新加的课自动纳入检查，谁再把 `focusQuizAnswer` / `focusQuizResult` 删掉或挪错位置都会当场失败。

## 仍需人工确认的部分

脚本能证明「Tab 顺序不断、焦点不丢、控件按得动」，下面这些还得人来看：焦点环的视觉观感（粗细、对比度、
在深色块上够不够醒目）、读屏软件实际念出来的顺序与语气、窄屏与移动端软键盘下的表现，以及
「只用键盘做题觉得别扭不别扭」这种主观感受。课程目录页上，焦点停在某张课卡时按 `↑` / `↓` 不会切换课程
（课卡本身是 `<button>`，方向键被页面让给了按钮自己的语义），这是已知的取舍，留给下一轮评估。
